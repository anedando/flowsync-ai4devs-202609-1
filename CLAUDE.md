# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

FlowSync is a two-service project used as a teaching exercise: a complete AdonisJS 7 auth API (`backend/`) and a bare React 19 + Vite frontend (`frontend/`) that still needs its UI built out. The two apps are independent (no shared package/workspace root, no shared types package) and talk to each other over HTTP.

**The backend already exists and is not to be modified in the frontend-login exercise this repo is set up for.** Treat `backend/` as a stable, finished API to read and consume, not to extend — unless the user explicitly asks for a backend change.

## Commands

### Backend (`backend/`, AdonisJS 7)

```bash
cd backend
npm install
cp .env.example .env && node ace generate:key   # first-time setup only
node ace migration:run                           # apply DB migrations (sqlite, backend/tmp/db.sqlite3)
npm run dev                                      # serve with HMR, http://localhost:3333
npm run build                                    # node ace build
npm test                                         # node ace test (Japa)
npm run lint                                     # eslint .
npm run format                                   # prettier --write .
npm run typecheck                                # tsc --noEmit
```

Run a single test file: `node ace test tests/functional/some_file.spec.ts`. Test suites are declared in `backend/adonisrc.ts` (`unit` → `tests/unit/**/*.spec.ts`, `functional` → `tests/functional/**/*.spec.ts`); neither directory exists yet, only `tests/bootstrap.ts`.

### Frontend (`frontend/`, React 19 + Vite)

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173
npm run build       # tsc -b && vite build
npm run lint        # oxlint
npm run preview
```

The frontend has no formatter configured and no test runner set up.

Run backend and frontend in separate terminals; both must be up for the app to work end to end.

## Backend architecture

AdonisJS request flow, in the order a request passes through them:

- **Route** (`backend/start/routes.ts`) — maps a URL to a controller action. All API routes are under `/api/v1`, split into an unauthenticated `auth` group (`POST /auth/signup`, `POST /auth/login`) and an authenticated `account` group (`GET /account/profile`, `POST /account/logout`) guarded by `middleware.auth()`.
- **Middleware** (`backend/app/middleware/*.ts`, wired in `backend/start/kernel.ts`) — `auth_middleware.ts` enforces the `api` guard on protected routes; `silent_auth_middleware.ts` attempts auth without failing; `force_json_response_middleware.ts` forces JSON everywhere.
- **Controller** (`backend/app/controllers/*.ts`) — thin: validates via a VineJS validator, calls the Lucid model, serializes the result. See `access_tokens_controller.ts` (login/logout), `new_account_controller.ts` (signup), `profile_controller.ts`.
- **Validator** (`backend/app/validators/user.ts`, VineJS) — `signupValidator` requires `fullName` (nullable), `email` (unique), `password` + `passwordConfirmation`; `loginValidator` requires `email` + `password`. Tickets written in product language often omit fields like `passwordConfirmation` that the validator actually requires — check the validator, not just the ticket, before wiring a frontend form.
- **Model** (`backend/app/models/user.ts`, Lucid) — `User` composes the generated `UserSchema` with `withAuthFinder` (gives `User.verifyCredentials()`) and exposes `User.accessTokens` (a `DbAccessTokensProvider`) for issuing/revoking API tokens.
- **Transformer** (`backend/app/transformers/user_transformer.ts`) — whitelist of fields returned to clients (`id`, `fullName`, `email`, `createdAt`, `updatedAt`, `initials`); keeps `password` out of responses.
- **Migration** (`backend/database/migrations/*.ts`) — versioned schema changes; never hand-edit the schema. `backend/database/schema.ts` is auto-generated by `node ace migration:run` from the migrations — it is regenerated, not edited.

Auth model: token-based (`config/auth.ts`, `api` guard, prefix `oat_`), not session cookies, even though a `web` session guard is also configured. The frontend must store the token returned by signup/login and send it (`Authorization: Bearer <token>`) on subsequent requests. CORS (`config/cors.ts`) allows all origins in dev and sends `credentials: true`.

Responses are wrapped by a custom `serialize()` helper added to `HttpContext` in `backend/providers/api_provider.ts`: non-paginated JSON bodies come back as `{ data: ... }`. Controllers call `serialize(...)`, not `response.json(...)`.

Subpath imports are used throughout instead of relative paths, as declared in `backend/package.json#imports` (`#controllers/*`, `#models/*`, `#validators/*`, `#transformers/*`, `#middleware/*`, `#database/*`, `#start/*`, `#config/*`, etc.) — mirror this convention in new backend files.

## Frontend architecture

`frontend/` is currently the unmodified Vite React-TS starter (`App.tsx` is template boilerplate); the real UI (signup, login, protected profile view) has not been built yet. The project README mentions shadcn/ui as the intended component source, but no shadcn setup or dependency exists yet in `frontend/package.json` — it needs to be initialized before use. Linting is via oxlint (`frontend/.oxlintrc.json`), not ESLint.


## Reglas de proceso
- Antes de tocar código: crear una rama nueva (`git checkout -b feat/<slug>`). Nunca
commitear directo en `main`/`s1/start`.
- Al cerrar la tarea: usar la skill `/commit`, luego `gh pr create` con una descripción
completa de los cambios en el cuerpo del PR.
- Después de abrir el PR: usar el subagente `adversarial-reviewer` sobre él, antes de
darlo por terminado.
- No repitas ese resumen en el chat: la sesión se va a perder, el PR no. Responde solo
con la URL del PR.
